## 2. 方法頁 `/method`

「我們怎麼確定每一段都接得上」。往下捲時一段一段展開，一共十段（0～9）：

0. 先把所有可能都列出來（幾種組合：場次 × 餐廳）
1. 第一關：趕得上開演
2. 第二關：走路不超過上限
3. 第三關：趕得上點餐（包括有沒有營業）
4. 第四關：趕得上回程車
5. 第五關：不超過預算（每人多少錢，電影、餐點、車資各多少）
6. 五關都過的才留下（幾種每段都接得上 → 挑出幾個）
7. 緩衝怎麼算（這個例子最緊的一段，以及寬鬆、剛好、偏緊的分界）
8. 為什麼要查最早到、最晚走的車（一條時間線圖）
9. 資料從哪來、多久更新

**數字從哪來**：每一關配一個真數字，來自真後端範例（`backend-plan-result.json`）的**第 1 個方案**，由 `methodFacts.ts` 取出。某個數字取不到就整個不顯示，不會編。畫面上標「示範」。

**為什麼不列每一關刪掉幾組**：排成功時後端只回「一共幾種組合、幾種每段都接得上」，沒有每一關各刪幾組，我們不編造（決定 D14）。關卡順序照後端檢查的順序：開演、走路、營業和最後點餐、回程車、預算。

**班次查詢怎麼寫**：頁面只說「排行程時向交通部查班次，同一時段的結果最多暫存 6 小時」，不說「每次即時查」（後端有 6 小時的路線快取）。

細節：

- 第 7 段寫「少於 {snug} 分算偏緊」。原本計畫寫「{snug} 分以下」，會跟「剛好」的範圍在 10 分那一格重疊，所以改了，數字照 `BUFFER_LEVELS`。
- 電腦版左邊有一條細的進度提示（`aria-label="這一頁的段落"`），手機不顯示。
- 減少動態（`prefers-reduced-motion`）時，十段一開始就全部顯示。**列印時也每一段都顯示**（`@media print` 把透明度和位移拿掉）。
- 第 9 段的更新時間只在後端有回狀態時才寫，沒有就不寫。

## 3. AI 助理頁 `/ai`

教使用者把 ZeroGap 接進 Claude。內容：可以這樣說（範例）、怎麼接上、助理會用到的六個工具、做不到的事。

**MCP 網址怎麼決定**（`mcpUrl.ts`，有單元測試），照順序：

1. `VITE_PUBLIC_MCP_URL`
2. `VITE_API_BASE` + `/mcp`
3. 同網域的 `/mcp`

假資料模式（展示站）沒有網址可以給：頁面直接說「這個展示站沒有接上真的後端」，不顯示網址，也不顯示 Claude Code 那一卡。

接法分三種：Claude 桌面版或網頁版（加自訂連接器，貼網址）、Claude Code（一行指令加 MCP 伺服器）、其他支援 MCP 的助理。複製按鈕的「已複製」放在螢幕閱讀器念得到的狀態區；複製失敗會叫使用者手動選取。

**同網域 `/mcp` 要真的轉得過去**：`vite.config.ts` 的開發代理和 `nginx.conf` 都加了 `/mcp`。nginx 那一段**這次沒有實際跑過**（這台機器沒有 nginx，用 Docker 測要下載映像檔，所以沒測），只用眼睛對過設定，上線前要試一次。

**後端要對外上線才接得到**。後端部署（D12）不在這次範圍，所以現在展示站的 `/ai` 只能講怎麼接，不能真的接。

六個工具名稱照 `backend/app/mcp.py`，一字不改：`list_areas`、`search_locations`、`list_stations`、`list_categories`、`data_coverage`、`plan_date`。

## 6. 「排行程」偶爾沒反應

症狀：整套測試平行跑時，iPad（有時 iPhone）專案偶爾按了「排行程」網址卻停在首頁，約四百次一次。

**找到的原因**：不是點擊被吞掉，是**點擊根本沒落在按鈕上**。

- 商圈清單還沒載入時的灰色佔位，比載入後真的商圈按鈕寬。在 iPad（兩欄）和 iPhone（一欄）上，佔位要排成兩行，真的只要一行。
- 清單一載入好，版面縮短，「排行程」整個往上跳 44px（iPad）／48px（iPhone）。桌機四欄時兩者都是兩行，不會跳，所以只有觸控專案出事。
- 按下去的瞬間（mousedown）和放開（mouseup）之間，如果剛好清單載入好、按鈕跳走，mouseup 的位置已經在按鈕下面的卡片上，瀏覽器就把 click 送給卡片，按鈕的 `onClick` 從頭到尾沒跑。
- 排除了：晚上換日期的規則（D15）、牆上時鐘、「記著的點擊沒被送出」的邏輯。

**怎麼修**（`QuickPlanForm.tsx`）：

- 佔位改成跟真的商圈按鈕一樣的外框、字級，裡面放跟目前四個商圈同樣字數的全形空白（`AREA_NAME_LENGTHS`），寬度和換行就跟真的一樣。單元測試把這個字數表和假後端的商圈名稱綁在一起，改了商圈名稱忘了改佔位，測試會失敗。
- 載入中按下去：按鈕變成「準備中…」（`aria-busy`），不會重複送出；載入好自動送出。
- 超過 10 秒還沒載入好：收起「準備中…」，說明「資料還沒載入好」，附「再試一次」。

假後端加了兩個預覽情境：`?mock=slow_lists`（清單晚 2 秒）、`?mock=lists_hang`（清單一直不回）。

**還沒做**（之後另外處理）：日期自動修正的說明（晚上開啟、日期被往後改一天）出現時，也可能讓按鈕位置移動，回訪的使用者可能遇到，屬於同一類問題。

## 7. 測試數字和效能

- 單元測試：38 個檔案、268 個測試，全過。
- Playwright 流程測試（`npm run predemo`，chromium、webkit、iPhone、iPad 四個專案）：362 個，全過。
- 無障礙（axe，WCAG 2.1 A／AA，日、夜各一輪）：十二個頁面，嚴重和重大問題為零。新加的 `/method`（先設減少動態，十段全顯示）、`/ai`、`/about` 都過；`/behind` 日、夜兩輪都過。
- 效能（`npm run perf`，慢速 4G）：首頁 **LCP 1.87 秒**（FCP 也是 1.87）、精靈第 1 步 1.82 秒；一般 4G 首頁 0.56 秒。目標是小於 2.0 秒，過。
- 打包隔離：`recharts` 只在 `FunnelCharts` 那一包（366 kB，幕後頁延遲載入）；真後端範例 JSON 只在 `backend-plan-result` 那個獨立的包，只有方法頁和幕後頁用。首頁的包（`index`）裡只有它的檔名（延遲載入的對照表），沒有 recharts、沒有範例 JSON（只有首頁「示範」用的三個數字：73,038、1,201、3）。
