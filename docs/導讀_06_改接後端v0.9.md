# 導讀 06：改接後端規格書（v0.9 → v0.13）

> 2026-10-20～21。前端原本照我們自己寫的 `docs/API.md` 做，後端組員另外寫了一份規格書。這一版把前端改成照後端規格書串接，並跟到後端實作時的 v0.13。分支 `feature/backend-v0.9`。

---

## 1. 一句話

**送出的條件、收到的結果、等待的方式都換了**：條件一律送代碼和 id；結果是「結構化的時間軸」，句子由前端自己組；一次規劃要 2～3 分鐘，所以用 SSE 串流一邊等一邊看進度；系統拿不定時不再插一頁，而是在結果頁直接「換一部／換一家」。

## 2. 跟後端講話的方式

| | 以前（API.md） | 現在（後端規格書 6.2～6.7） |
|---|---|---|
| 下拉選單 | 一支 `GET /api/options` 全包 | 縣市 → 商圈 → 出發站 → 類別 → coverage（有場次的日子、當天的電影） |
| 條件 | 中文名稱，例如「中壢站」「日式」 | 代碼和 id，例如 `origin_station_id: 49`、`cuisine: "japanese"`；「不限」「幫我挑」都送 `null` |
| 規劃 | `POST /api/itineraries`，等一下就回 JSON | `POST /api/plans`，回 **SSE 串流**：`queued`（排第幾位）→ `progress`（做到哪一步）→ `result` 或 `error` |
| 時間軸 | 後端寫好句子 | 後端只給 `transit`、`walk`、`movie`、`wait`、`meal`、`home` 六種步驟和時間、地點，句子由 `shared/lib/steps.ts` 組 |
| 系統拿不定 | 閥門沒過就插一頁問使用者 | 結果照樣出來，`alternatives` 附上其他候選，使用者在結果頁換 |
| 無解 | 後端給放寬建議 | `NO_FEASIBLE` 只給「各條件擋下幾組」，放寬按鈕由前端算 |

**SSE 是什麼？** 比喻：後端用「一封一封的明信片」寄進度過來，每封中間空一行。網路可能把一封切成好幾段送到，所以 `api/sse.ts` 先收進信箱，湊滿一封才拆。瀏覽器內建的 `EventSource` 只能用 GET，這支是 POST，所以用 `fetch` 自己讀。

## 3. 檔案地圖

| 檔案 | 做什麼 |
|---|---|
| `api/schemas.ts` | 驗貨單（zod）：後端送來的每個欄位先檢查一次，格式不對立刻報錯 |
| `api/sse.ts`、`api/client.ts` | 拆明信片；各端點的出入口；錯誤一律變成 `PlanError {code, reasons, retryAfter}` |
| `api/planRuns.ts` | 規劃的「叫號機」：同時只跑一個、換條件就取消舊的、畫面離開就取消、結果存在瀏覽器（重新整理不重跑） |
| `api/benchmark.ts` | 簡報模式接真後端時，把基準案例的車站和日期換成真的 |
| `features/result/PlanProgress.tsx` | 等待畫面：排隊順位、七個階段一格一格打勾、「1,880 種組合 → 39 種接得上」，可以取消 |
| `features/result/Timeline.tsx` | 大時間軸；電影、用餐那一步底下掛「換一部／換一家」，交通那一步底下掛「其他班次」 |
| `features/result/swap.ts`、`Alternatives.tsx` | 換一部／換一家的計算和畫面 |
| `features/result/NoSolution.tsx`、`relax.ts` | 無解：列原因＋一鍵放寬一級 |
| `shared/brand/Attribution.tsx` | Google Maps 標誌、OpenStreetMap 出處 |
| `mocks/` | 假後端：用**真的 SSE 串流**送出（還故意把封包切斷），所以拆串流的程式在假資料模式也會跑到 |

## 4. 使用者看得到的改變

### 等待畫面（取代約 3 秒的五道關卡動畫）

一次規劃 2～3 分鐘，人多還要排隊，所以照後端送來的進度推進：「排隊中，你是第 2 位」→ 讀資料 → 查車 → 篩組合（顯示組合數）→ 挑 3 個 → 確認營業時間 → 查精確班次 → 排時間軸。交通查詢每分鐘有次數限制，排隊等候時會多一行說明。可以按「取消規劃」，回到精靈第 4 步。

### 換一部／換一家（決策 Q104）

後端的 `alternatives` 有哪一項，就在那一步底下出現「這幾部也接得上，想換一部嗎？」。換了以後：

- 方案卡、花費區的到家時間和每人花費換成**估計值**（黃底）
- 時間軸上方加一行「時間軸仍是原本的 XX；換成 YY 的到家時間和花費是估計」
- 一次只能換一項（後端的估計是各自對原方案算的，不能疊加）
- 換電影時如果搭配的餐廳也不同，會寫「餐廳也會跟著換成 ZZ」

### 其他細節

| 情況 | 畫面 |
|---|---|
| 營業時間沒核對過（`hours_verified: false`） | 用餐那一步：「營業時間未確認，請向店家確認」 |
| Google 額度用完、沒有店名 | 改顯示料理類別：「一家日式餐廳」 |
| 餐廳來自 Google | 時間軸、路線示意卡片底部放 Google Maps 標誌（官方檔案，不可修改） |
| 餐廳來自 OpenStreetMap | 時間軸底部寫出處，連到 OSM 版權頁 |
| 示意資料（`demo`） | 不用標 |
| 回程 | 「8 分鐘後發車，錯過的話 22:28 前還有車」 |
| 跨午夜 | 時刻前面加「隔天」；時間滑桿可以到隔天 02:00 |
| 同名的車站 | 「桃園站」（台鐵）、「高鐵桃園站」、「機捷高鐵桃園站」 |
| 商圈 | 從後端讀：桃園區、中壢、八德、蘆竹（南崁）；青埔目前不開放 |

### 系統幕後

- 用瀏覽器裡最近一次成功的規劃；還沒排過就用假資料範例（標「範例」），不為了範例去打後端（每個 IP 每小時只能規劃 10 次）
- 漏斗只有三層：全部組合 → 每段都接得上 → 給你的方案（後端這一版不給每關各剔除幾組）
- 機率表多了「誰決定」：哪幾項由 LLM 代選
- 資料來源照 `/api/status`：Jev 正式版或模擬版、LLM 有沒有連上、四個資料的更新時間
- MCP 已經由後端提供（`/mcp` 的 `plan_date`）

## 5. 假資料情境

網址加 `?mock=…`（只在假資料模式有效）：

| 參數 | 情境 |
|---|---|
| `no_solution` | 預算 $800 以下時無解，可以按「每人預算改成 $800」 |
| `low_confidence` | 第 1 案附電影、餐廳備選；第 2 案附回程的其他班次 |
| `no_showtimes` | 這天沒有符合條件的場次 |
| `queue_full` | 排隊已滿（HTTP 503） |

假資料的第 3 案是 OSM 來源、營業時間沒核對過，可以看到出處和提醒。

## 6. 測試

- 單元測試（Vitest）：SSE 被切斷、CRLF、心跳、多行 data；`postPlan` 用假的 fetch 回 SSE 和 503；**用後端真正的回應**（`src/api/__fixtures__/backend-plan-result.json`，後端 `tools/contract-check` 收的）驗證 zod；時間軸句子、跨午夜「隔天」、回程句子；放寬按鈕；換一部／換一家；Google 地圖連結的 place_id 規定
- 流程測試（Playwright）：有解（等待畫面、Google 標誌、OSM 出處）、取消、無解一鍵放寬、沒場次、排隊已滿、低信心換一家、改條件、試用、簡報、手機兩條

## 7. 接真後端

```bash
cp .env.example .env    # 把 VITE_USE_MOCK 改成 false
npm run dev             # /api 自動轉給 localhost:8000
```

後端在專案根目錄 `docker compose up -d` 啟動。注意：後端的資料是當天起抓的，只有抓到的那幾天有場次；精靈會自動把沒資料的日子灰掉。
