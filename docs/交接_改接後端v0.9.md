## 2. 任務內容（原始需求）

把組員的前端 ZeroGap 從它自己的 `docs/API.md` 合約，改成照後端規格書串接：

- `/api/counties`、`/api/areas`、`/api/stations`、`/api/categories`、`/api/coverage`、`/api/status`、`POST /api/plans`。
- `/api/plans` 回傳 **SSE**，用 `fetch`＋ReadableStream 讀 `queued`、`progress`、`result`、`error`；串流開始前也可能直接回 JSON 錯誤 409、429、503。
- 請求一律送代碼或 id，「不限」「幫我挑」都送 `null`；沒資料的日子用 `available_dates` 灰掉；**飲食限制整個拿掉**。
- 結果頁：時間軸改成結構化步驟（`transit`、`walk`、`movie`、`wait`、`meal`、`home`）＋每一步的 `buffer_*`、`place`；Google 來源餐廳顯示 Google 標誌；地圖連結用 Maps URLs（`destination_place_id` 一定要同時帶 `destination`）；SVG 示意圖不依座標擺 Google 來源的餐廳。
- 低信心：拿掉「插一頁先挑再重送」，改成結果頁用 `alternatives` 換一部／換一家。
- 等待畫面：依 `queued` 順位、`progress` 階段和組合數推進，要撐得了 2～3 分鐘；後端不給每關剔除數。
- 無解：`error` 事件的 `NO_FEASIBLE`（附 `reasons`）、`NO_SHOWTIMES`。
- 系統幕後、狀態列改成新的 `/api/status` 和結果格式。
- 假資料（`VITE_USE_MOCK=true`）和 GitHub Pages 展示版要照樣能跑有解、低信心、無解三種情境。
- 更新單元測試和 Playwright；另寫給組員的白話說明 `docs/導讀_06_改接後端v0.9.md`（風格照導讀 01～05）。

**v0.9 跟 v0.8 不同的三點**（規格書已更新）：

1. `alternatives` 的電影、餐廳備選只附估計值：餐廳 `{restaurant_id, name, cuisine, probability, home_at, cost_per_person_total, estimated: true}`、電影 `{movie_id, title, …}`。換了以後**只更新到家時間和每人花費，標成估計值，時間軸不換**。路線備選是 TDX 精確值 `{summary, depart_at, arrive_at, fare_per_person, probability}`。
2. `highlight`：第一名固定 `{"key":"recommended","label":"最推薦",…}`；第二、三名從 `cheapest`、`safest`、`earliest_return`、`shortest_walk` 分配，可能是 `null`。
3. `buffer_gate` 是 `return_trip` 的那一步多一個 `return_window`：`{planned_depart_at, minutes_to_planned, latest_depart_at, minutes_to_latest}`，`buffer_minutes` 等於 `minutes_to_latest`。畫面可以寫「8 分鐘後發車，錯過的話 22:28 前還有車」。

**完成標準**：`tsc`、`npm test`、`npm run build` 通過；Playwright 有跑（裝不了瀏覽器要說明）；改動 commit 在 `feature/backend-v0.9`，commit 照慣例 `feat(scope): …`；最後 `git format-patch main..feature/backend-v0.9 -o <資料夾>` 產生補丁給前端組員。

**規則**：規格書和 `docs/前端決策紀錄.md` 都沒涵蓋的 UI 決定，先問使用者，不要自己決定。

## 4. 我自己做的實作選擇（回報時要讓使用者知道，必要時再確認）

- **等待畫面有「取消規劃」**：一次要 2～3 分鐘，給一個取消的出口；按了取消並回到精靈第 4 步（ResultPage 還沒接）。畫面也寫「離開這一頁會取消規劃」，因為後端在斷線時會取消工作。
- **從精靈按「排出接得上的行程」一定重新規劃**，不用瀏覽器裡的舊結果；**重新整理**才用瀏覽器存的結果、不重播（Q62）。
- **系統幕後**在還沒有自己的結果時，顯示假資料的範例（標「範例」），不再為了範例去打後端（每個 IP 每小時只能規劃 10 次）。
- **一次只能換一項**：電影和餐廳都有備選時，換了電影就取消換餐廳，反之亦然（後端的估計是各自對原方案算的，不能疊加）。
- **409 `PLAN_IN_PROGRESS` 自動重試**：每 2 秒、最多 3 次（換條件時舊的規劃可能還沒被後端放掉）。
- **OSM 來源的餐廳標出處**（還沒做）：查過 OSMF 的署名指南，要寫 OpenStreetMap 並連到 `https://www.openstreetmap.org/copyright`。打算在用到 OSM 店家的卡片底部寫「餐廳資料來自 OpenStreetMap」。這點規格書討論紀錄寫「還沒查證」，回報時要提。
- **Google 標誌放的位置**：時間軸卡片底部、路線示意卡片底部（同一個容器內，照官方規定）。複製出去的文字因為放不了圖，加一行「餐廳資料：Google Maps」。

- 假資料的「有場次的日期」是今天起 14 天（空一天），並保證包含基準案例的 2026-10-30；**10/30 以後跑流程測試會失敗**，要把 `benchmarkRequest.date` 改到之後的日子（`lib.test.ts` 裡的「10/30（五）」也要跟著改）。
