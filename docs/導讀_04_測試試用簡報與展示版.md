# 導讀 04：流程測試、試用模式、簡報工具、GitHub Pages 展示版

> 對應時程：第 11–12 天（決策 Q90）。後端還沒好，所以先做這些「發表會用得到」的東西。

---

## 1. 一句話

現在有一個指令能自動把整個網站走過一遍（流程測試）；找同學試用時會自動記秒數和問卷（試用模式）；上台時按數字鍵就能跳關（簡報模式）；也準備好了一個評審用手機就能打開的公開網址（GitHub Pages，**還沒發布**）。

## 2. 流程測試（Q77、Q89）

**比喻**：請一個機器人照劇本把網站從頭點到尾，任何一步不對就大叫。

```bash
npm run e2e
```

| 劇本 | 驗證什麼 |
|---|---|
| 有解 | 介紹頁 → 四步精靈 → 篩選動畫 → 三個方案；估計值真的是黃底（驗收 A8）；切到「最穩」後網址變 `plan=2`、時間軸換成 17:05 出發 |
| 無解 | 預算 $500 卡在「每人不超過 $500」；按「每人預算改成 $800」後有解 |
| 低信心 | 先問「想看哪一部」，挑完重算，網址寫入片名 |
| 改條件小視窗 | 預算改 $1,500 →「重算」→ 網址和花費區同步 |
| 試用模式 | 計時＋問卷，紀錄出現在系統幕後 |
| 簡報模式 | 按 2 排「週末午後，先吃再看」，按 B 到系統幕後 |

每個劇本在 **Chromium（Chrome 核心）和 WebKit（Safari 核心）** 各跑一次，共 12 個，全部通過。WebKit 很重要，因為 iPhone 上的瀏覽器都是 Safari 核心，評審掃 QR code 就是用它。

另外，`npm test` 是 37 個「單元測試」，只測計算邏輯（緩衝分級、網址轉換、試用統計…），比流程測試快很多。

## 3. 試用模式（Q79、Q80）

**怎麼用**：找同學試用時，打開 `http://localhost:5173/?trial=1`。

1. 進介紹頁開始計時；
2. 進精靈時記「看懂用途花了幾秒」；
3. 三個方案出現時記「拿到行程花了幾秒」；
4. 右下角跳出 3 題小問卷：黃底代表什麼？願不願意照這個行程出門（1–5）？比自己查快嗎？
5. 送出後按「下一位試用者」，條件清空、回到首頁重新計時。

**看結果**：系統幕後最下面多了「試用紀錄」，有平均秒數、1 分鐘內完成的人數、答對黃底的人數，可以下載或複製 CSV（Excel、Google 試算表都能開）。

這些數字直接對應 MVP 的成功指標：「30 秒內理解網站用途」「1 分鐘內拿到可執行的行程」。發表時講「10 位同學平均 48 秒拿到行程」比講「很快」有力（Numbers tell）。

紀錄只存在那台電腦的瀏覽器裡，不會上傳。`?trial=0` 關閉。

## 4. 簡報模式（Q95）

**怎麼用**：網址加 `?present=1`。

| 按鍵 | 效果 |
|---|---|
| 1／2／3 | 直接用第 1／2／3 張情境卡排行程，播完整篩選動畫 |
| B | 跳到系統幕後 |
| H | 回首頁 |

整體字級放大 15%，投影時後排也看得清楚；右下角有一行小提示。只對「這個分頁」有效，關掉分頁就恢復正常。在輸入框打字時不會誤觸。

## 5. GitHub Pages 展示版（Q78、Q96）

**還沒發布**，只準備好了，要你同意後才推上 GitHub（公開網址，任何人都看得到）。

準備好的東西：

| 檔案 | 作用 |
|---|---|
| `.github/workflows/pages.yml` | 推到 GitHub 的 main 分支後自動：安裝 → 跑單元測試 → 打包 → 發布 |
| `npm run build:pages` | 打包成「放在 `/repo名稱/` 底下」的版本，並複製一份 `404.html`，讓深層網址直接打開也不會 404 |
| `public/og.png` | 貼到 LINE 時顯示的預覽圖（`npm run og` 重新產生） |
| `index.html` 的 og 標籤 | 預覽圖的標題、說明、圖片網址 |

展示版**固定用假資料**，畫面上會一直顯示「假資料（開發用）」標籤，不會讓人誤以為是真實場次。

已經用正式打包版在 `/zerogap/` 底下實測：換頁、延遲載入的系統幕後、直接打開結果頁網址都正常，沒有錯誤。
